`locale.cc` is OSv's locale core: `setlocale()`, `newlocale()`, `duplocale()`, `freelocale()`,
`uselocale()` and `nl_langinfo_l()`. It gives the answers glibc gives with the distribution's
standard C.utf8 installed (Debian/Ubuntu libc-bin, Fedora glibc): the C locale (also spelled POSIX)
and C.UTF-8 (any C.<UTF-8 codeset>[@modifier] spelling). Other names fail with ENOENT.
`langinfo-builtin.inc` holds glibc's nl_langinfo values for those two locales; it is generated by
`scripts/gen-langinfo-builtin.py` from glibc observations, and `tests/tst-locale-builtin.cc` checks
the same behaviour (it passes on glibc too). The C locale object (`c_locale`, with the ctype
tables) is defined in runtime.cc.

Multibyte conversion (`libc/multibyte/multibyte.cc`) follows LC_CTYPE as glibc's does: in C only
bytes 0..0x7f are characters and MB_CUR_MAX is 1; in C.UTF-8 it is UTF-8 and MB_CUR_MAX is 6.
`tests/tst-locale-ctype.cc` checks it, and passes on glibc too. One deliberate difference: glibc
encodes wide characters 0x200000..0x7fffffff as 5- and 6-byte sequences, while OSv's `wcrtomb()`
and `wctomb()` fail with EILSEQ there, because musl's stdio converts into 4-byte (MB_LEN_MAX)
buffers. Those values are never Unicode. The decoder accepts the 5- and 6-byte forms as glibc does.
`iconv()` decodes UTF-8 input as Unicode only, in any locale (as it did before): a form above
U+10FFFF is EILSEQ. glibc's iconv rejects such a form when converting to UTF-16 or UTF-32, but
passes it through to UTF-8, WCHAR_T and UCS-4.

Wide stdio (`libc/stdio/fputwc.c`, `fputws.c`, `fgetwc.c`, `ungetwc.c`, `vswprintf.c`, `vswscanf.c`,
`open_wmemstream.c`, OSv copies of musl's) follows glibc too, and `tests/tst-locale-ctype.cc` checks
it against glibc's answers. A byte-backed stream converts in the locale bound at its first wide
operation: output of a character that locale cannot encode writes its C transliteration
(`__osv_c_translit`, generated from glibc) in C, or '?', and succeeds; input of an invalid sequence is
WEOF with EILSEQ and an error, with the bytes left unread (a sequence truncated by end of file is
consumed); `ungetwc()` of any character succeeds. The wide-buffer streams (`swprintf()`,
`swscanf()`, `open_wmemstream()`, flagged F_WBUF in `stdio_impl.h`) never convert, so any wchar_t
value round-trips. Known differences from glibc:
- `fputwc(WEOF)` on a byte-backed stream writes '?' and returns WEOF (glibc writes nothing and
  returns 0), because musl's `vfwprintf()` passes WEOF for a `%c` it cannot convert and glibc writes
  '?' there.
- `ftell()` after `ungetwc()` subtracts the pushed-back bytes (as musl's does; 5 for a character the
  stream's locale cannot encode), where glibc gives 0 on an unread stream and -1 otherwise.
- Wide calls on a byte-oriented stream (`fgetwc()`, `fputwc()`, `fputws()`, `fwprintf()`) work
  instead of failing.
- A stream bound to C writes the C transliteration even when LC_CTYPE is C.UTF-8 at the call (glibc
  uses the current locale's, so 0xe9 becomes 'e').
- `fgetws()` leaves errno EAGAIN on success.

The other files in this folder provide a minimal implementation of the rest of the locale functionality. Unfortunately musl 1.1.24 had enhanced
its implementation to support categories (for example new 'cat' field in locale struct)
and does not quite fit OSv minimal need. For now, we have made minimal changes to existing
files and mostly retained older musl 0.9.12 copies to make locale-specific logic work.
We may need to adjust it futher and decide what files constitute OSv version
of it and completely cut it off of any future musl upgrades.

Please see following musl commits that should shed some light:
- https://git.musl-libc.org/cgit/musl/commit/?id=0bc03091bb674ebb9fa6fe69e4aec1da3ac484f2 (add locale framework)
- https://git.musl-libc.org/cgit/musl/commit/?id=16f18d036d9a7bf590ee6eb86785c0a9658220b6 (byte-based C locale, phase 2: stdio and iconv (multibyte callers))
- https://git.musl-libc.org/cgit/musl/commit/?id=61a3364d246e72b903da8b76c2e27a225a51351e (overhaul locale internals to treat categories roughly uniformly)
